# Review fix pass: wiring filters, live loop hardening, buffer cap (v2)

The fix commit addresses all seven issues from the v1 review. Premium/discount filtering is implemented in the entry model, OTE and order blocks are wired as non-blocking confluence indicators, the live loop now exits on initial connection failure and attempts reconnection on mid-session drops, daily P&L is tracked via balance delta, the candle buffer is capped at 500, the backtester's SL-first assumption is documented, and credentials support environment variable overrides.

**Watch for:** The premium/discount filter is structurally correct inside `generate_entry_signal()` but never receives HTF data in either `main.py` or `backtester.py` — no code calls `set_htf_range()` or passes `htf_swing_high`/`htf_swing_low`, so the guard is dead in production (confirmed). The daily P&L tracker uses function-attribute state (`run_live._day_start_balance`) which is fragile and has a race with the midnight reset logic that could double-reset the baseline (likely). The `get_open_positions()` call result is discarded unused (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The premium/discount filter rejects longs in premium and shorts in discount using the equilibrium midpoint, but it's gated behind `self.htf_swing_high is not None`, and nothing in the live loop or backtester ever sets those values. The filter will never fire until someone calls `entry_model.set_htf_range(high, low)` with values derived from D1/H4 candles. This is the same functional gap as v1 issue #1, now relocated: the code exists but remains unreachable from the execution paths.

The daily P&L fix uses `balance - day_start_balance` which correctly tracks realized P&L (MT5 balance only changes on position close). However, the implementation stores state as function attributes on `run_live` and the midnight reset block clears `daily_pnl` to 0 without resetting `_day_start_balance`, creating a desync window on connection hiccups.

1. **Premium/discount filter unreachable** — `set_htf_range()` is never called in `main.py` or `backtester.py`. The live loop needs to fetch D1/H4 candles at startup (and periodically) and pass the swing range to the entry model. Without this, the filter is dead code.
2. **Daily P&L baseline desync at midnight** — The `current_day` reset block sets `daily_pnl = 0.0` but does not reset `run_live._day_start_balance`. 3. **Dead `get_open_positions()` call** — The positions variable is fetched every loop iteration but the result is passed through an empty `if` block (`pass`). This is wasted API overhead and the `known_tickets` set is never populated.

## Premium/discount filter is wired but never activated

The entry model's `generate_entry_signal()` now correctly guards:

```python
if self.htf_swing_high is not None and self.htf_swing_low is not None:
    equilibrium = calculate_equilibrium(self.htf_swing_high, self.htf_swing_low)
    if direction == "long" and is_premium(entry_price, equilibrium):
        return None
    if direction == "short" and is_discount(entry_price, equilibrium):
        return None
```

The problem is upstream: `run_live()` instantiates `EntryModel()` with no arguments, leaving both values as `None`. The config includes `timeframes.htf: [D1, H4]` but no code fetches those candles to derive the swing range. The fix requires adding HTF data fetching (e.g., `connector.get_candles(symbol, "D1", 20)` at startup and on day-change) and calling `entry_model.set_htf_range(daily_high, daily_low)` with detected swing points. Without this, the bot still takes longs in premium and shorts in discount.

## Daily P&L uses function-attribute state with a desync window

The implementation stores `_day_start_balance` and `_day_start_date` as attributes on the `run_live` function object:

```python
if not hasattr(run_live, '_day_start_balance'):
    run_live._day_start_balance = balance
if now.date() != getattr(run_live, '_day_start_date', None):
    run_live._day_start_balance = balance
    run_live._day_start_date = now.date()
daily_pnl = balance - run_live._day_start_balance
```

Two problems. Function-attribute state persists across calls to `run_live()` if invoked multiple times in the same process. More concretely, the midnight reset block at the top of the loop sets `daily_pnl = 0.0` but doesn't touch `_day_start_balance`. If `account_info` returns `None` on that iteration (connection hiccup), `balance` stays at the fallback 10000 and `_day_start_balance` retains yesterday's value, producing a nonsensical delta until the next successful fetch.

Fix: store `day_start_balance` as a local variable alongside `daily_pnl` and reset both in the midnight block.

## Silent connection death won't trigger reconnection

The `connector.connected` flag is only set to `False` by the wrapper's own `disconnect()` method. If the MT5 socket dies silently (network partition, broker restart), the flag remains `True` and `get_candles()` returns `None` indefinitely. The reconnection logic checks `if not connector.connected` and will never trigger. Consider treating N consecutive `None` returns from `get_candles()` as a disconnection signal.
