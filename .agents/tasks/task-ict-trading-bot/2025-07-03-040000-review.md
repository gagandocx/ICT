# ICT Sequential Entry Bot for NAS100

A greenfield trading bot implementing Inner Circle Trader concepts as a Python state machine. The architecture decomposes ICT methodology into independent analysis modules (market structure, FVG, liquidity, kill zones, OTE, premium/discount, order blocks) and orchestrates them through a sequential confirmation entry model: liquidity sweep, then MSS, then FVG, then limit order at the FVG midpoint. The bot supports live trading via MetaTrader 5 and offline backtesting through historical CSV replay.

**Watch for:** The entry model does not enforce the premium/discount filter or use order blocks/OTE despite these modules existing (confirmed). The live trading loop has no mechanism to track open position P&L for daily loss accounting (confirmed). Credentials are loaded from a plaintext YAML file with no guidance on secrets management (confirmed). The backtester's SL/TP evaluation assumes SL is always hit first when both levels are breached in the same candle (likely).

## High-level view

The entry model state machine is the core integration point but only wires three of the seven ICT analysis modules (liquidity, market structure, FVG). Premium/discount filtering, OTE zone validation, and order block confluence are implemented as standalone modules with full APIs but are never called during trade decisions. The bot will take entries in premium zones for longs and discount zones for shorts, contradicting the stated trading rules.

The live loop in `main.py` tracks `daily_pnl` but never updates it from closed positions. It resets at midnight and accumulates nothing, so the 3% daily loss circuit breaker is effectively dead in live mode. The backtester independently implements daily P&L tracking correctly, making this an asymmetry between the two execution paths.

The MT5 connector degrades gracefully on non-Windows platforms, returning failure dicts instead of crashing. However, the live loop treats connection failure as "monitoring mode" but still attempts to fetch candles and place orders through the disconnected connector on every iteration — no reconnection logic, no backoff, no early exit.

## Entry model wiring gap: premium/discount, OTE, and order blocks are dead code

The `premium_discount.py`, `ote.py`, and `order_blocks.py` modules are fully implemented with clear APIs (`is_premium`, `is_discount`, `calculate_ote_zone`, `is_price_in_ote`, `find_order_blocks`). None of them are imported or referenced in `entry_model.py` or `main.py`'s live loop. The user requirement explicitly states "Only long in discount, short in premium" as a rule, and OTE (62-79% retracement) as an entry concept. The entry model currently generates a short signal after a sweep-high -> bearish MSS -> bearish FVG sequence without checking whether the entry price sits in a premium zone.

The order blocks module's `find_order_blocks` takes structure events as input and could serve as a confluence filter (only enter if entry price is within an unmitigated OB zone), but this integration doesn't exist. The bot will trade against its own stated rules until these modules are wired into the decision path.

## Daily P&L tracking is broken in live mode

In `run_live()`, the `daily_pnl` variable is initialized to 0 and reset at midnight. The live loop's architecture is fire-and-forget: it places a limit order via `connector.place_order()` and then resets the entry model. There is no polling for position status, no `on_trade_close` callback, no periodic check of `connector.get_open_positions()` to detect filled/closed trades.

The backtester handles this correctly by simulating SL/TP hits candle-by-candle and accumulating `daily_pnl` inline. The live loop would need a position tracking thread or a poll-on-tick mechanism to update P&L.

The consequence: the 3% daily loss limit (`can_take_trade`) never triggers in live mode. The bot will continue entering trades after any number of losses in a single day.

## Backtester same-candle SL/TP ambiguity

In `_check_trade_exit`, for a long trade the method checks `candle["low"] <= trade["stop_loss"]` before checking `candle["high"] >= trade["take_profit"]`. When a volatile candle spans both levels, the trade is always recorded as a loss. This biases backtest results pessimistically without disclosing the policy.

For NAS100 on 1-minute data during news events or session opens (exactly when kill zones are active), same-candle SL/TP breach is plausible. At minimum, document the assumption; ideally, offer a configurable mode.

## Live loop continues operating after connector failure

```python
result = connector.connect(...)
if not result["success"]:
    print(f"MT5 Connection: {result['message']}")
    print("Continuing in monitoring mode (no live trading)...")
```

After this message, the loop enters `while True` with the same connector object. Every 10 seconds it calls `connector.get_candles()` which returns `None` (since `self.connected` is False), so the entry model never receives data and the loop is a silent no-op polling forever.

There's no reconnection logic — if the initial connect fails or the connection drops mid-session, the bot sits idle permanently until manually restarted.

## Candle buffer growth

`EntryModel.candle_buffer` is appended to on every `update()` call and only cleared on `reset()`. For the Asian session (20:00-00:00 ET, 4 hours), if no signal fires the buffer accumulates 240 candles. The `check_liquidity_sweep` method builds a DataFrame from the full buffer on every tick. If `reset()` is missed (e.g., a bug in KZ boundary detection around midnight), the buffer grows indefinitely. A sliding window or max-size cap would be more defensive.

## Credential handling

The config example stores MT5 credentials and Telegram bot token as plaintext YAML values. The `load_config` function reads the file directly with no environment variable interpolation, no keyring integration, no `.env` fallback. For a trading bot handling real broker credentials, this is a security gap worth addressing before live deployment — at minimum, support `${ENV_VAR}` expansion in the YAML loader or document the expected secrets management approach.

## Test coverage gaps

Not tested: the `main.py` live loop and backtest runner (integration-level), the Telegram notifier's HTTP behavior, `logger.py` file I/O, and the full end-to-end path from raw candle data through sweep detection, MSS, FVG, and signal generation as a single integrated sequence. The entry model tests stop at state advancement (`test_sweep_advances_state_to_waiting_for_mss`) without completing the full cycle to signal generation with realistic candle data that exercises all three detection stages sequentially.
