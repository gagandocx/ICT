# MQL5 Expert Advisor port of ICT Sequential Entry Model

A single 1651-line MQL5 file replicates the entire Python ICT bot as a Strategy Tester-compatible Expert Advisor. The sequential state machine (Sweep -> MSS -> FVG -> Entry), all detection algorithms, kill zone time windows, premium/discount filtering, OTE and Order Block confluence, risk management, and position sizing are translated from the Python modules. The EA runs on M1 bars, gates entry logic behind kill zone checks and a daily loss limit, and places pending limit orders (BUY_LIMIT / SELL_LIMIT) with SL/TP via `OrderSend`.

Watch for:
- **Server time assumption** (likely): The EA assumes server time equals UTC. Brokers using UTC+2 or UTC+3 will have kill zones firing 2-3 hours early. No broker-offset input exists.
- **Buffer trimming can corrupt stored indices** (confirmed): After trimming oldest candles, `sweep_index`, `break_index`, and `swing_index` are decremented by `excess` without bounds checking. Negative indices cause subsequent detection to accept any MSS unconditionally.
- **No pending order expiry** (confirmed): Limit orders placed with `ORDER_TIME_GTC` persist indefinitely. Unfilled orders from a prior kill zone remain active across sessions — a behavioral gap not present in the Python backtester.
- **Asian kill zone midnight boundary** (confirmed): The `et_total < 0` check is dead code because `ServerTimeToET` wraps negatives to positive. Both Python and MQL5 effectively cover 20:00-23:59 ET only (consistent behavior).

## High-level view

The state machine is an exact replica: four states advanced strictly in sequence, reset on kill zone exit or after entry attempt. Each detection function operates on identical algorithmic logic — same loop structures, comparison operators, and selection criteria (most-recent sweep, highest bearish FVG by `high`, lowest bullish FVG by `low`).

Kill zone times match `config/settings.yaml`. The DST calculation manually implements US rules (2nd Sunday March, 1st Sunday November). The material concern is the assumption that `TimeCurrent()` returns UTC — most brokers use UTC+2 or UTC+3, which would shift all kill zones. Using `TimeGMT()` or exposing a `ServerUTCOffset` input would fix this.

Risk management defaults match exactly: 1% risk, 3% max daily loss, `volume = (balance * risk%) / (SL_distance * contract_size)`. The MQL5 daily PnL tracking queries deal history (including commissions and swap), which is more comprehensive than the Python simulation.

Limit orders have no expiry mechanism. The Python backtester never faces unfilled limits because it sets `active_trade` immediately. The live EA can accumulate stale orders from prior kill zones that fire hours or days later at prices no longer relevant.

## Buffer index corruption after trimming

When the buffer exceeds `MaxBufferSize` (500), the oldest `excess` candles are removed and stored indices are adjusted:

```mql5
if(g_sweep_valid)
   g_sweep_info.sweep_index -= excess;
if(g_mss_valid)
{
   g_mss_info.break_index -= excess;
   g_mss_info.swing_index -= excess;
}
if(g_fvg_valid)
   g_fvg_info.index -= excess;
```

No check ensures these remain non-negative. If the sweep occurred at buffer index 50 and 100 candles are trimmed, the resulting `sweep_index = -50`. The next `CheckMSS` call uses this as the threshold: `mss_events[i].break_index > sweep_idx`. Since `sweep_idx` is negative, every MSS event passes, potentially advancing state with an MSS that chronologically preceded the sweep.

The Python version avoids this because `self.candle_buffer[-max_buffer_size:]` discards indices entirely — all detection functions re-scan from scratch. The MQL5 code tries to preserve cross-state references which creates this edge case.

Fix: after the index adjustment block, add:

```mql5
if(g_sweep_valid && g_sweep_info.sweep_index < 0)
   { g_sweep_valid = false; g_state = STATE_WAITING_FOR_SWEEP; }
if(g_mss_valid && (g_mss_info.break_index < 0 || g_mss_info.swing_index < 0))
   { g_mss_valid = false; g_state = STATE_WAITING_FOR_SWEEP; }
if(g_fvg_valid && g_fvg_info.index < 0)
   { g_fvg_valid = false; g_state = STATE_WAITING_FOR_SWEEP; }
```

## Kill zone timing: server time vs UTC

The `CheckForNewBar` function passes `candle.time` (from `CopyRates`) to `GetActiveKillZone`. `CopyRates` returns server time, which varies by broker. The Python backtester operates on CSV timestamps assumed to be UTC.

For Strategy Tester, server time is whatever the broker's history uses (often UTC+2 for EET brokers). This means the same EA will produce different results on different broker histories unless the UTC assumption holds.

The fix is straightforward: replace `candle.time` with `TimeGMT()` at the kill zone check, or compute:

```mql5
datetime utc_time = candle.time - TimeGMTOffset();
string kz_name = GetActiveKillZone(utc_time);
```

## Order lifecycle gap

The backtester's model is: signal -> immediately set `active_trade` -> simulate SL/TP fill on subsequent candles. There is no concept of an unfilled pending order.

The MQL5 EA places a limit order at the FVG midpoint. If price never retraces to that midpoint, the order sits open. On the next kill zone entry, `HasActiveTradeOrOrder()` returns `true` and the EA skips processing — effectively blocking new setups until the stale order is manually cancelled or filled. This could suppress the EA for extended periods if a high-momentum move creates FVGs whose midpoints are never revisited.

Options: cancel unfilled orders on state reset, use `ORDER_TIME_DAY`, or set a `GTC + expiry datetime` via `request.expiration`.
